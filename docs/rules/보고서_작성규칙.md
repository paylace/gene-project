# 실험 보고서 작성 규칙

문서 버전: 1.0. 제정일: 2026-10-15. 적용 대상: 새로 작성하거나 개정하는 모든 공식 실험·후속 진단·구현 검증 보고서.

## 1. 반드시 지킬 사항

1. 실험마다 고유한 ID와 별도 보고서 파일을 만든다. 목적·계획·결과·일지를 하나의 긴 문서에 계속 붙이지 않는다.
2. 결과의 좋고 나쁨과 무관하게 실행 조건·실패·수정·제외 여부를 기록한다.
3. 보고서의 **마지막 절 제목을 `수행·작성·검토 기록`으로 하고, 누가 실험했는지 반드시 적는다.** 부록과 참고자료도 이 절보다 앞에 둔다.
4. 실험 수행자, 연구 요청자, 보고서 작성자, 검토자를 구분한다. 사용자가 요청했다는 이유로 사용자가 실행했다고 쓰지 않는다.
5. 정확한 모델명·버전을 확인할 수 없으면 `실행 당시 정확한 모델 ID 미기록`으로 쓴다. 대화에 언급된 모델명을 추정해 넣지 않는다.
6. 자동 테스트 통과·원자료 감사와 독립 검토를 구분한다. 별도 검토자가 없으면 `독립 검토 기록 없음`으로 쓴다.

## 2. 파일과 문서 상태

- 공식 위치: `docs/reports/`.
- 파일명: `실험ID_내용.md`. 예: `Q1-001_이동수집_본실험.md`.
- 실험 구분: 사전 조건 고정 본 실험 / 예비 실행 / 탐색적 후속 실험 / 사후 진단 / 구현·재현 검증 중 사실에 맞게 적는다.
- 상태: 계획 초안 / 실행 중 / 실행 중단 / 실행 완료·작성 중 / 작성 완료·독립 검토 미완료 / 독립 검토 완료 등을 구분한다.
- `실행 완료`는 모든 목표가 달성됐다는 뜻이 아니다. `검사 통과`를 연구 결론 전체의 검증 완료로 표현하지 않는다.
- 사후 정리한 과거 실험 보고서에는 실행일과 문서 정리일을 따로 적고, `기존 실행 기록의 분리·작성본`이라고 밝힌다.

## 3. 보고서의 필수 내용

세부 제목은 과제에 맞게 조정할 수 있지만 다음 내용은 빠지면 안 된다.

| 내용 | 독자가 알 수 있어야 할 것 |
|---|---|
| 식별 정보 | 실험 ID, 제목, 구분, 버전, 상태, 실행일·작성일 |
| 연구 질문 | 무엇을 확인하며 어떤 결과가 주장을 지지하거나 제한하는가 |
| 대상과 방법 | 환경, 관측, 행동, 상태 전이, 학습·진화·동결 조건 |
| 비교와 평가 | 대조군, 선발 방법, 지표, 독립 시드, 에피소드·반복 수, 데이터 분할 |
| 결과 | 주 지표·보조 지표·불확실성·실패 사례, 해당 원자료 링크 |
| 오류와 변경 | 발생 시점, 원인, 수정, 영향받은 데이터와 처리. 모르면 미기록이라고 명시 |
| 해석과 한계 | 관측한 사실, 가능한 설명, 미확인 원인을 구분 |
| 결론과 다음 질문 | 사전 질문에 대한 답과 그 결론이 적용되는 조건 |
| 재현 | 작업 디렉터리, 명령, 코드·설정·데이터·로그 위치 |
| 마지막 수행 기록 | 수행자·작성자·모델 기록·독립 검토 상태 |

조건이 많거나 긴 코드가 있으면 프로토콜·원자료로 연결하되, 보고서만 읽어도 핵심 방법과 지표는 이해할 수 있어야 한다.

## 4. 수치와 해석

- `%`와 `%포인트`를 구분한다. 정확도 80%→70%는 −10%포인트다.
- `시드 10개 × 에피소드 504개 × 난수 3반복`에서 독립적인 탐색 반복은 시드 10개다. 모든 에피소드를 독립 실험으로 세지 않는다.
- 평균·표준편차·구간이 어느 단위에서 계산됐는지 쓴다. 시드 변동 구간이 새로운 환경 전체를 보장한다고 쓰지 않는다.
- 학습 중 보상, 선발셋 성적, 테스트 성적을 구분한다. 주 지표가 낮다고 보조 지표로 성공의 뜻을 바꾸지 않는다.
- 차이를 확인하지 못한 결과를 동등성 증명이나 일반적인 능력 부재로 표현하지 않는다.
- 기억 정확도, 과제 성공률, 기억 지연 스텝, 학습 에피소드 수는 서로 다른 양이다.
- 조건 제거와 그 조건 없이 재훈련·재진화한 결과를 구분한다.
- 실험자가 행동을 보완한 성적, 수작업 규칙, 손으로 만든 신경망은 개체가 자력으로 획득한 성적으로 보고하지 않는다.

## 5. 사전 계획과 사후 진단

실행 전에 조건과 판정을 저장했는지, 이미 본 결과가 설계에 영향을 주었는지 쓴다. 결과를 본 뒤 설계한 진단은 실행 전에 명세를 저장했어도 `사후 탐색`이다. 사용한 테스트셋을 다시 쓰면 재사용 사실을 기록한다. 보고서를 나눴다는 이유로 새 확인 실험이 된 것처럼 쓰지 않는다.

## 6. 오류·수정·보존

실행 실패, 환경 권한 오류, 라이브러리 부재, 집계 오류 등을 연구 성능 실패와 구분한다. 수정 전 원자료를 삭제하거나 불리한 시드만 제외하지 않는다. 작성상의 오탈자 수정과 과학적 결론 변경을 나누고, 후자는 일지에 이전·이후와 이유를 남긴다. 오류가 기록되지 않았다는 것을 오류가 없다는 증명으로 사용하지 않는다.

## 7. 마지막 절의 필수 필드

아래 항목은 모두 있어야 한다. 알 수 없는 값은 비워 두지 말고 미기록·확인 불가로 쓴다.

- 연구 방향·실험 요청자
- 실험 수행자와 실제 역할: 예를 들어 로컬 프로그램 작성·명령 실행·집계
- 실험 수행일
- 보고서 작성자와 역할
- 문서 작성일 또는 정리일
- 사용 모델·버전의 기록 여부: AI가 관여한 경우
- 독립 검토자·검토 범위·상태: 없으면 없다고 명시

현재 보고서의 `Codex`는 이 대화에서 로컬 도구를 사용한 AI 에이전트를 가리킨다. 정확한 모델 ID가 저장되지 않은 과거 실행은 그 사실을 그대로 적는다. 새 실험에서는 확인 가능한 도구·모델 식별 정보도 실행 명세에 남긴다.

## 8. 제출 전 점검

- [ ] [양식](../templates/실험보고서_양식.md)의 필수 내용을 채웠다.
- [ ] 분류·지표·시드·비교·원자료·명령을 확인했다.
- [ ] 실패와 사후 탐색을 숨기지 않았다.
- [ ] 마지막 절에 실제 수행자·작성자·검토 상태가 있다.
- [ ] 완료 보고서에 `<입력>` 같은 미작성 표시가 없다.
- [ ] [보고서 목록](../reports/README.md), 현황, 일지에서 찾을 수 있다.
- [ ] 문서 링크와 수행자 표기를 관리 검사기로 확인했다.

원본 보존용 역사 문서는 내용을 소급 변경하지 않는다. 그런 자료는 공식 보고서와 구분해 보존 위치·작성 주체의 확인 가능 범위를 안내한다. 연구 코드가 자동 생성한 집계 Markdown도 공식 보고서를 대신하지 않는다.
